# Implement Customer CRM Enhancements in the Backend

You are working on the existing BookingSaaS backend, built with ASP.NET Core, Entity Framework Core, PostgreSQL, and ASP.NET Core Identity.

Your task is to enhance the existing Customer management functionality without changing unrelated parts of the project.

## 1. Inspect the Existing Implementation First

Before making any changes, inspect the existing:

- Customer entity and its relationships.
- Customer DTOs.
- CustomerController and its authorization rules.
- CustomerService and its interface.
- DbContext configuration.
- Existing FluentValidation validators.
- Existing booking-related entities and their relationships with Customer.
- Existing migration conventions.

Follow the current project architecture and naming conventions.

**Important:** Do not assume that the existing implementation matches this prompt exactly. Inspect the actual code first. If an architectural ambiguity or potentially destructive relationship is discovered, stop and report it instead of guessing.

## 2. Customer Entity Updates

Keep all existing Customer properties and add the following fields:

| Property | Type | Requirement |
|---|---|---|
| Email | string? | Optional |
| IsActive | bool | Default value: true |
| CreatedAt | DateTime | Automatically assigned when created |
| UpdatedAt | DateTime? | Updated whenever customer information changes |

The final Customer entity should contain:

- Id
- Name
- PhoneNumber
- Email
- Notes
- IsActive
- CreatedAt
- UpdatedAt
- BusinessId

Do not add `Address`, `BirthDate`, or `Tags`.

Do not create a relationship between Customer and ApplicationUser. Customer records must continue to follow the existing business-scoped architecture.

Preserve all existing relationships and avoid breaking existing data.

## 4. Customer CRUD Endpoints

Preserve the existing endpoint structure:

Base route:

`/api/business/{businessId}/customers`

Implement or update the following endpoints.

### GET /

Return all customers belonging to the specified business.

Response:

`CustomerDto[]`

### GET /{customerId}

Return a single customer.

The customer must belong to the specified business.

Return 404 if the customer does not exist or does not belong to that business.

### POST /

Create a customer.

Request body:

```json
{
  "name": "علی رضایی",
  "phoneNumber": "09123456789",
  "email": "ali@example.com",
  "notes": "مشتری دائمی"
}
```

Requirements:
- BusinessId must come from the route, not the request body.
- Id must be generated by the backend.
- IsActive must default to true.
- CreatedAt must be assigned automatically.
- UpdatedAt must initially be null.
- Return the created CustomerDto.

### PUT /{customerId}

Update an existing customer.

Request body:

```json
{
  "name": "علی رضایی",
  "phoneNumber": "09123456789",
  "email": "ali@example.com",
  "notes": "مشتری VIP",
  "isActive": true
}
```

Requirements:
- Only update the customer belonging to the specified business.
- Do not allow changing Id or BusinessId through the request.
- Update UpdatedAt automatically.
- Return the updated CustomerDto.

### DELETE /{customerId}

Add a customer deletion endpoint.

Requirements:
- The customer must belong to the specified business.
- Return 404 if the customer does not exist or does not belong to that business.
- Preserve existing authorization and business ownership rules.
- Do not delete related bookings, appointments, or historical records.

Before implementing deletion, inspect the actual database relationships and delete behaviors.

If hard deletion could violate foreign-key constraints or destroy booking history, use an appropriate soft-delete approach only if it fits the existing architecture. Otherwise, stop and report the issue before implementing a potentially destructive solution.

Do not silently cascade-delete historical data.

## 5. Authorization and Business Ownership

Preserve the existing authorization rules.

Allowed roles:
- Admin
- BusinessOwner

For BusinessOwner:
- They must own the business specified in the route.
- They must not access or modify another business's customers.
- All customer queries and mutations must remain scoped to BusinessId.

Do not weaken authorization to make an endpoint work.

Do not introduce access for Customer or Employee roles.

Keep the existing Admin behavior unless the current implementation clearly requires a change. Do not introduce unrelated authorization changes.

## 6. Validation

Use the project's existing FluentValidation approach.

Validate:

- Name: required and has a reasonable maximum length.
- PhoneNumber: follow existing project conventions and support valid Iranian mobile numbers without overly restrictive validation.
- Email: optional, but validate its format when provided.
- Notes: optional, with a reasonable maximum length.
- IsActive: must be a valid boolean value.

Use the existing Persian API validation/error response conventions.

Do not introduce a new validation framework.

## 7. Database Migration

Create an EF Core migration for the new Customer fields.

Requirements:
- Preserve all existing customer records.
- Give existing records a safe default for IsActive.
- Populate CreatedAt for existing records using an appropriate migration-safe default.
- Ensure UpdatedAt remains nullable.
- Do not drop or reset any existing tables.
- Do not delete or recreate the database.

Follow the existing migration naming and configuration conventions.

## 8. Constraints

- Do not add Address.
- Do not add BirthDate.
- Do not add Tags.
- Do not link Customer to ApplicationUser.
- Do not create a new Booking or Appointment architecture.
- Do not modify unrelated endpoints or entities.
- Do not refactor unrelated services or controllers.
- Do not change the existing authentication or token implementation.
- Do not reset the database or remove existing data.
- Do not add automated tests as part of this task.

If an existing design decision conflicts with these requirements, explain the conflict before making a potentially breaking change.

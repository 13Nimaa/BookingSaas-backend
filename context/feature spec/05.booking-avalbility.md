# Phase 4 — Booking Availability API

**Project:** `E:\BookingSaas-backend`

**Previous phases:**
- Phase 1: Booking domain foundation — complete.
- Phase 2: Employee-Service Management API — complete.
- Phase 3: Booking Creation API — complete.

**Objective:** Implement a reliable availability API that returns bookable time slots for a specific business, service, employee, and date.

Read `AGENTS.md` and the relevant context documentation first. Follow the existing architecture and conventions. Do not repeat previous phase audits.

## 1. Inspect the Relevant Existing Implementation

Inspect only:
- `WorkingHour` entity and its configuration.
- `Business.TimeZoneId`.
- `Booking` entity and `BookingStatus`.
- `Service.DurationMinutes`.
- `Employee`, `EmployeeService`, and their relationships.
- Existing BookingService and BookingController.
- Existing DTO, validation, and error-response conventions.

Determine how WorkingHour records represent:
- Business working days.
- Employee-specific working hours, if supported.
- Date-specific schedules.
- Breaks or multiple working intervals, if supported.

Do not invent support for schedules or breaks that do not exist in the current domain model.

If the existing WorkingHour model cannot represent the required availability rules, stop and report the exact limitation before changing the domain model.

## 2. API Endpoint

Implement:

`GET /api/bookings/availability`

Query parameters:
- `businessId`
- `serviceId`
- `employeeId`
- `date`

The date represents a calendar date in the business's local timezone.

Return available slots with:
- StartTime
- EndTime

Use a consistent response DTO. Return timestamps in an explicitly documented format. Prefer ISO 8601 timestamps with UTC offsets so the frontend can interpret the business-local time correctly.

## 3. Validation

Verify:
- Business exists and is active according to existing rules.
- Service belongs to the selected business.
- Employee belongs to the selected business.
- Employee is assigned to the selected service.
- Date is valid.
- Business has a valid configured timezone.
- Required working-hour records exist for the requested date/day.

Return clear Persian validation errors consistent with the existing API.

Do not expose data belonging to another business.

## 4. Availability Calculation

Calculate slots using:
- Business-local working hours.
- Service.DurationMinutes.
- The employee's existing schedule, if the current model supports it.
- Existing bookings for the selected employee.

The following booking statuses occupy time:
- Pending
- Confirmed

The following statuses do not occupy time:
- Cancelled
- Expired
- Completed

Use half-open intervals `[start, end)` so adjacent bookings can be scheduled without treating their boundary as an overlap.

A slot is available only if:
- The entire service duration fits inside the applicable working interval.
- It does not overlap an active booking.
- It satisfies the existing schedule constraints.

Do not return slots in the past.

## 5. Timezone and UTC Rules

- Interpret the requested date in `Business.TimeZoneId`.
- Interpret WorkingHour values in business-local time.
- Convert generated slot boundaries to UTC for comparison with Booking timestamps stored in PostgreSQL.
- Convert returned slots to the documented response format.
- Handle daylight-saving transitions safely for timezones that observe them.
- Do not assume the server's local timezone.
- Do not hardcode `Asia/Tehran` in availability calculations; use the business's configured timezone.

## 6. Slot Generation

Use a consistent slot interval.

Before choosing the interval:
- Check whether the project already defines a booking slot interval or scheduling increment.
- If it does, reuse it.
- If it does not, use a configurable 15-minute default rather than hardcoding it throughout the implementation.

Avoid returning duplicate slots.

## 7. Performance

- Query only bookings relevant to the selected employee and requested date range.
- Filter occupying statuses at database level.
- Avoid loading all bookings into memory.
- Reuse existing indexes where appropriate.
- Avoid unnecessary database queries inside slot-generation loops.

## 8. Integration with Booking Creation

Do not assume that calling the availability endpoint reserves a slot.

Availability is informational. Two users may request the same slot concurrently.

Do not claim that this phase prevents race conditions or guarantees a slot remains available until booking creation.

The booking-creation endpoint must eventually enforce overlap protection transactionally or through an appropriate database constraint. That belongs to a later phase.

## 9. Tests

Add focused integration tests following the existing test conventions.

Cover at least:
1. Returns slots within working hours.
2. Does not return slots that exceed the working interval.
3. Excludes Pending bookings.
4. Excludes Confirmed bookings.
5. Does not exclude time occupied only by Cancelled bookings.
6. Does not exclude time occupied only by Expired bookings.
7. Uses the service duration correctly.
8. Rejects an employee not assigned to the service.
9. Rejects an employee or service belonging to another business.
10. Handles business timezone conversion correctly.
11. Does not return past slots.
12. Handles adjacent bookings using half-open interval semantics.

Do not introduce a new testing framework.

## 10. Scope Restrictions

Do NOT implement:
- Booking expiration BackgroundService.
- Owner approval or status-transition APIs.
- Transactional overlap protection during booking creation.
- PostgreSQL exclusion constraints.
- Appointment modifications.
- Frontend changes.
- Unrelated refactoring.

Do not apply migrations.

If schema changes are genuinely required, create a migration but leave it unapplied and explain the reason.

5. Timezone conversion strategy.
